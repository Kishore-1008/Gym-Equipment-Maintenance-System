# Gym Equipment Maintenance System

Full-stack app: a static HTML/CSS/JS frontend backed by a **Java 17 + Spring Boot + MySQL** REST API.

```
HTML + CSS + JavaScript
        |
Spring Boot REST API  (backend/)
        |
Spring Data JPA
        |
MySQL Database

```

## Project layout

```
backend/    Java 17 / Spring Boot / Maven — REST API, auth, MySQL access
frontend/   Static site (HTML/CSS/JS), calling the API

```

## Features

- User Registration & Login against MySQL (BCrypt password hashing, JWT sessions)
- Role-Based Authorization (Admin, Gym Manager, Technician) — enforced on the backend
- Admin: Add / View / Update / Delete / Search / Filter equipment
- Equipment IDs (EQ001, EQ002, ...) generated by the backend
- Equipment Name -> Category mapping enforced by the backend
- Usage Monitoring: number of usage sessions per equipment per day (Admin + Gym Manager dashboards — summary cards, usage table, history/trend, top used equipment; Gym Manager also gets a Batch Usage Logging screen to enter a whole zone at once)
- Responsive UI using Bootstrap 5

## No default account

There is **no seeded admin account** and **no hardcoded credentials**. The database starts with zero users and zero equipment. Create your first account (as any role, including Admin) through the Create Account page.

## How to run the application

The application has three parts involved in normal operation:

1. **MySQL database** — must be running.
2. **Spring Boot backend** — runs from `backend/` on port `8080`.
3. **Static frontend** — served locally, normally on port `5500`.

> **Important:** Do not open `login.html` directly by double-clicking the file or by using a `file://` URL. The frontend must be served through HTTP (for example, VS Code Live Server), otherwise browser CORS restrictions can prevent requests from reaching the backend.

### 1. Open the project

Open the project folder in VS Code:

```text
Gym-Equipment-Maintenance-System/
```

The Maven project is inside:

```text
Gym-Equipment-Maintenance-System/backend/
```

Therefore, Maven commands must be executed from the `backend` directory.

### 2. Start MySQL

Make sure your local MySQL server is running.

Then open:

```text
backend/src/main/resources/application.properties
```

and set `spring.datasource.username` and `spring.datasource.password` for your local MySQL installation.

The database schema is:

```text
gym_ams
```

The required tables are created/updated automatically by Spring Boot/Hibernate on startup.

**MySQL does not need to be restarted every time the application is run — leave it running.**

### 3. Check whether port 8080 is already in use

The Spring Boot backend uses **port 8080**.

If an old backend instance is still running, starting another instance can fail with a message such as:

```text
Web server failed to start. Port 8080 was already in use.
```

On **Windows PowerShell**, check port 8080:

```powershell
netstat -ano | findstr :8080
```

Example:

```text
TCP    0.0.0.0:8080    0.0.0.0:0    LISTENING    12345
```

The last number (`12345` in this example) is the **PID (Process ID)**.

Identify the process:

```powershell
tasklist /FI "PID eq 12345"
```

If it is an old Java/Spring Boot process that you want to stop:

```powershell
taskkill /PID 12345 /F
```

Then verify that port 8080 is free:

```powershell
netstat -ano | findstr :8080
```

If nothing is returned, port 8080 is free.

> **If you started the backend using `mvn spring-boot:run` or `mvnd spring-boot:run` in a terminal that is still open, press `Ctrl+C` in that terminal instead. You do not need to use `taskkill`.**

> **Do not kill a process blindly. Always identify the PID with `tasklist` first so that you do not stop an unrelated application.**

## Usage Monitoring module

Tracks how many times each piece of equipment is used, per day — nothing more.

### Concept

Usage is measured only as a **session count**: how many usage occurrences a piece of equipment had on a given day.

```
Treadmill 01 → 8 sessions on 12-Aug-2026
Treadmill 02 → 5 sessions on 12-Aug-2026
Elliptical 01 → 0 sessions on 12-Aug-2026

```

There is no usage-hours tracking, no start/end time, no meter readings, no sensors/QR codes, and no gym-member accounts. Each equipment has **at most one usage record per date** — `(equipment, date)` is a unique key. Saving again for the same equipment and date updates that day's record instead of creating a duplicate, and historical days are never overwritten by a later day's entry.

```
UsageRecord
├── id
├── equipment (→ existing Equipment entity)
├── usageDate
└── sessionCount

```

### Roles

- **Admin** — views the full dashboard (summary, table, history, top-used) and can delete a usage record.
- **Gym Manager** — sees the same dashboard, plus the **Batch Usage Logging** screen, since it's the role responsible for entering usage data (matches the existing permission structure: `POST`/`PUT` on `/api/usage/**` is Gym-Manager-only, `DELETE` is Admin-only, `GET` is open to both).
- **Technician** — unaffected; this module doesn't touch that dashboard.

"Zone" in the spec maps to the equipment's existing **category** field (`Cardio` / `Strength`) — no separate zone concept or duplicate equipment list was introduced. Usage records always reference the existing `Equipment` entity.

### Dashboard sections

Both `admin-dashboard.html` and `gym-manager-dashboard.html` render the same four sections (via the shared `usage-dashboard.js`):

1. **Summary cards** — Total Sessions, Most Used Equipment, Least Used Equipment, Total Equipment, for the currently selected date.
2. **Usage Table** — every piece of equipment (optionally filtered by zone) for one selected date, with columns `Equipment | Zone | Sessions | Usage Status`. Equipment with no logged record yet for that date still shows a row at 0 sessions / "Not Used" rather than being omitted.
3. **Usage History** — pick one equipment and view its sessions over time as a small bar chart plus a date/sessions table, with Daily / Weekly / Monthly grouping and a trending up/down/stable indicator.
4. **Top Used Equipment** — ranking by total sessions over the last 30 days.

The Gym Manager dashboard additionally has:

5. **Batch Usage Logging** — pick a zone and a date, and every piece of equipment in that zone appears in one table with a session-count input already pre-filled from that day's existing data (if any). One **Save All Sessions** click saves/updates every row in a single request — no clicking into separate equipment pages.

### Usage Status thresholds

Status is derived from `sessionCount`, never stored, and controlled by one constant:

```
// backend/src/main/java/com/gymams/model/UsageStatus.java
public static final int HIGH_THRESHOLD = 7;

```

| sessionCount Status       |          |
| ------------------------- | -------- |
| 0                         | Not Used |
| 1 – (HIGH\_THRESHOLD − 1) | Normal   |
| ≥ HIGH\_THRESHOLD         | High     |

Change `HIGH_THRESHOLD` to retune what counts as heavy use.

### Usage Monitoring API

All endpoints are under `/api/usage`. Auth follows the existing JWT/role pattern (`Authorization: Bearer <token>`).

| Method Path Role Purpose  |                                                                  |                    |                                                                        |
| ------------------------- | ---------------------------------------------------------------- | ------------------ | ---------------------------------------------------------------------- |
| GET                       | `/api/usage?zone=&date=`                                         | Admin, Gym Manager | Usage Table for one date, optional zone filter                         |
| GET                       | `/api/usage/summary?date=`                                       | Admin, Gym Manager | Summary cards for one date (defaults to today)                         |
| GET                       | `/api/usage/history?equipmentId=&groupBy=day\|week\|month&days=` | Admin, Gym Manager | History/trend for one equipment                                        |
| GET                       | `/api/usage/top?days=&limit=`                                    | Admin, Gym Manager | Top-used ranking over a window (defaults: 30 days, top 5)              |
| POST                      | `/api/usage`                                                     | Gym Manager        | Save one `{equipmentId, usageDate, sessionCount}` — creates or updates |
| POST                      | `/api/usage/batch`                                               | Gym Manager        | Save one date's `{equipmentId, sessionCount}` list in one call         |
| PUT                       | `/api/usage/{id}`                                                | Gym Manager        | Correct an existing record's session count                             |
| DELETE                    | `/api/usage/{id}`                                                | Admin              | Remove a usage record                                                  |

### Notes for first run

- `spring.jpa.hibernate.ddl-auto=update` will add the new `usage_date` / `session_count` columns automatically. It will **not** drop old columns from a previous schema version (`log_date`, `usage_level`, etc.) if you're upgrading an existing database — on a dev database, simplest is to drop the `usage_record` table once and let Hibernate recreate it.
- No seed data — the table starts empty. Log in as a Gym Manager and use Batch Usage Logging to enter the first day's sessions.
